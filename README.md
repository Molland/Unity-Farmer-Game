## Контрольные вопросы

### 1. Зачем в команде запуска CLI использовать флаг `-nographics` и какую роль он сыграет, когда мы перенесем пайплайн на удаленный сервер в облако?

Флаг `-nographics` отключает инициализацию графического движка и видеокарты Unity. Он необходим для работы сборки на серверах, где отсутствует графическая оболочка.

При переносе пайплайна на удалённый сервер в облако данный флаг позволит выполнять сборку в режиме **Headless**, без необходимости в подключённом мониторе или графическом интерфейсе.

### 2. Что произойдет, если запустить консольную сборку проекта, в настройках Build Settings которого не выбрана ни одна сцена игры? Какая строка нашего кода обрабатывает эту ситуацию?

Если в `Build Settings` не выбрана ни одна активная сцена, сборка будет остановлена, а в лог будет выведено сообщение об ошибке.

Данную ситуацию обрабатывает условие:

```csharp
if (levels.Length == 0)
```

После него вызывается:

```csharp
ExitWithCode(1);
return;
```

Таким образом, при отсутствии активных сцен сборка не запускается.

### 3. Почему класс `BuildManager` и его методы обязательно должны быть объявлены как `public static`?

Класс и методы должны быть `public static`, потому что Unity вызывает метод сборки напрямую из командной строки через параметр:

```csharp
-executeMethod BuildManager.BuildWebGL
```

Unity должна иметь возможность найти класс `uildManager` и вызвать метод `BuildWebGL()` без создания экземпляра класса. Поэтому метод объявляется как `public static`.

## Контрольные вопросы

### 1. В чем заключается принципиальное различие между директивами `run` и `uses` в конфигурационном файле GitHub Actions?

`uses` подключает **готовое действие** (Action) из репозитория или Marketplace — упакованный, переиспользуемый компонент с определённым интерфейсом. `run` выполняет **shell-команды** напрямую на runner’е .

Проще говоря, `uses` — это «взять готовый кирпич», а `run` — «сделать что-то руками в терминале». Их можно freely комбинировать внутри одного Job’а .

### 2. Каким образом синтаксис языка YAML определяет вложенность и иерархию элементов, и какое ограничение накладывается на использование клавиши Tab?

YAML определяет иерархию через **отступы пробелами**. Увеличение отступа означает вложенность; элементы на одном уровне должны иметь одинаковый отступ .

Ограничение: **Tab использовать запрещено**. YAML допускает только пробелы для отступов . Если редактор смешивает Tab и пробелы, парсер может выдать ошибку или неверно интерпретировать структуру .

### 3. Какую роль играет директива `needs` в объявлении задач (Jobs) внутри файла `main.yml`, и что произойдет, если её не указать?

`needs` задаёт **явную зависимость между Jobs**. Если Job B имеет `needs: jobA`, то Job B не начнётся, пока Job A не завершится **успешно** .

Если `needs` не указать, Jobs по умолчанию выполняются **параллельно** (если нет других ограничений). Если Job A провалится, Job B будет **пропущен**, а не запущен с ошибкой .

### 4. Зачем в задаче зеркалирования (`mirror_repo`) используется параметр `fetch-depth: 0` для экшена `actions/checkout@v4`? Чем это отличается от дефолтного поведения экшена?

`actions/checkout` по умолчанию делает **shallow clone** с `fetch-depth: 1` — скачивает только последний коммит, чтобы сэкономить время и трафик .

`fetch-depth: 0` означает **полный клон** — вся история всех веток и тегов . Это критично для mirror-задач, потому что при зеркалировании нужно скопировать **всю историю репозитория**, а не только один коммит. Без `fetch-depth: 0` зеркало получится «урезанным» и непригодным для использования .

### 5. С какой целью секретные токены доступа (например, `BACKUP_TOKEN`) сохраняются в разделе Repository Secrets вместо прямого указания строки токена в коде пайплайна?

Repository Secrets хранятся **зашифрованными** и подставляются в workflow во время выполнения через `${{ secrets.BACKUP_TOKEN }}` .

Если токен указан прямо в коде пайплайна, он попадает в **историю Git** и становится видимым всем, у кого есть доступ к репозиторию. Даже если позже удалить токен из файла, он останется в предыдущих коммитах . Боты сканируют публичные репозитории на предмет утечек в течение секунд .

Дополнительно: Secrets позволяют **ограничить доступ** (например, только для production-среды), **ротировать** токены без изменения кода и **логировать** факт использования .

### 6. Какое системное событие (триггер) настроено в разработанном пайплайне для автоматического запуска рабочего процесса?

Без доступа к конкретному файлу `main.yml` невозможно назвать точный триггер. В GitHub Actions триггеры задаются в секции `on:`. Наиболее распространённые варианты для автоматического запуска :

- `push` — при пуше в ветку (например, `main`)
- `schedule` — по cron-расписанию
- `workflow_dispatch` — ручной запуск (не автоматический)
- `repository_dispatch` — внешний вебхук

Для «зеркалирования репозитория» наиболее вероятным автоматическим триггером является `schedule` (периодическое зеркалирование) или `push` (зеркалирование при изменениях).

### 7. Что такое концепция Sanity Check и почему автоматическая проверка соответствия индивидуального варианта должна выполняться на этапе `sanity_check` до запуска зеркалирования репозитория?

Sanity Check (проверка вменяемости) — это **быстрый базовый тест**, который проверяет, что результат или конфигурация в принципе может быть корректной, до запуска более дорогих и длительных операций .

В контексте пайплайна: `sanity_check` проверяет, что **индивидуальный вариант** (конфигурация, идентификатор, параметры) соответствует ожиданиям — например, что студент правильно указал свой вариант, что файлы существуют, что токены имеют доступ. Только после этого запускается **зеркалирование**, которое потребляет ресурсы (время, трафик, операции записи) .

Логика: если конфигурация неверна, зачем тратить ресурсы на зеркалирование? Sanity check отсеивает заведомо ложные или неполные данные **до** того, как дорогостоящая операция начнётся .
